1Executive Summary

The Solar Energy Prediction and Analysis Platform (internal codename Helios) is a full-stack web application that helps a non-specialist decide whether to install a solar photovoltaic (PV) system at a specific location, and gives a researcher the tools to interrogate hourly irradiance forecasting on the same data. It exposes two surfaces over one shared backend:

  • A consumer calculator (route /): a two-minute guided interview that returns expected annual generation, monthly and daily shapes, a confidence-rated range, an energy balance against the user's consumption, financial savings, payback, emissions avoided, and a shareable report — without asking the user to know what a kilowatt-peak is.
  • An analysis console (route /advanced): a fourteen-view research workbench that trains scikit-learn models on ERA5 reanalysis, validates them with time-aware splits and an embargo gap, calibrates prediction intervals with Conformalised Quantile Regression, and persists every run as a reproducible experiment.

Both surfaces run against the same deterministic physical chain (Erbs → HDKR → Faiman → PVWatts v5) and the same weather source (Open-Meteo Historical Weather API / ERA5 reanalysis). Machine learning is deliberately restricted to the forward-looking research path where predicting a specific future day is the actual task; the consumer answer is a climatology question, computed by running years of observed weather through the physics.

Problem addressed

Solar generation depends on location, orientation, weather, panel technology and the user's own consumption pattern. Existing reference apps often return the same number for morning and afternoon inputs or state impossible pairs like "16.79 kWh at 0 % irradiance". The platform's remit is to return an answer that is location-aware, time-consistent, physically defensible, and honestly bounded.

Major capabilities

  • Address search, GPS auto-locate, map-pin, and reverse geocoding.
  • Three ways to describe consumption (monthly bill, monthly kWh, or itemised equipment) and three ways to describe available space (single value, length × width, or polygon on a map).
  • Automatic tilt/azimuth search against the location's own weather.
  • Panel-count-first sizing, honouring existing systems and comparing scenarios.
  • Regional tariffs and currencies for 30+ countries; farm-subsidy detection.
  • Hourly self-consumption, battery dispatch and sizing, grid import/export ledger.
  • Full economics: CAPEX, savings, payback, ROI, LCOE, degradation-corrected lifetime yield, CO2 avoided with plain-language equivalences.
  • Measured uncertainty bands built from inter-annual weather variability and named assumption components; monthly ranges reflect each month's own spread.
  • Analysis console: 10 model families, rolling-origin cross-validation, five-check leakage audit, permutation importance, partial dependence, weather-regime error decomposition, anomaly detection, scenario analysis, and a Markdown report generator.

Outcome

A single-repository application (backend/ + frontend/) that runs locally with no API keys, produces a saved estimate in about a second against cached weather (up to ~15 s for a location never seen before), and completes a full model-trained analysis in 10–40 s. Backed by 223+ backend and 51 frontend automated tests.

2Introduction and Background

Photovoltaic energy is the fastest-growing electricity source globally, but its output is weather-dependent and therefore uncertain. That uncertainty makes three practical decisions difficult: sizing a system to match consumption, scheduling maintenance around expected generation, and balancing a grid that increasingly relies on variable resources. A prediction of solar generation is only useful if it is genuinely predictive of the future, states how uncertain it is, and has been validated in a way that mirrors deployment conditions.

Existing consumer solar tools mostly use a "sunlight × capacity" rule of thumb: they take a monthly kWh/m2 figure, multiply by system size, and print a number. That approach hides four problems: (i) it treats a national average as if it applied to a specific rooftop, (ii) it does not respond to time or orientation, (iii) it presents modelled figures without any range around them, and (iv) it cannot explain where its numbers came from. This platform was built to replace that class of tool with something that is transparent, location-aware and honest about what it does not know.

Why prediction is useful

  • Sizing. The right system size is the smallest one that meets the user's realistic offset target — not the biggest one that fits the roof. Getting this wrong wastes capital or under-produces for the life of the system.
  • Consumption matching. Solar generates when the sun is up. A household whose load is dominated by evening cooking recovers only a fraction of unstored generation through self-consumption; a farm whose pumps run during the day recovers most of it.
  • Financial planning. Payback depends on tariff, degradation, export policy and inter-annual weather variability; each of these is genuinely variable and each is stated openly here.
  • Grid operations. For an operator, hour-by-hour forecast accuracy with a calibrated range is the difference between a reserve that meets contingency and one that leaves a gap.

Challenges in estimating solar generation

  • Atmospheric attenuation is stochastic. Cloud, aerosol, humidity and precipitation move irradiance around by up to an order of magnitude within a single day.
  • Solar geometry is deterministic. Sun position, angle of incidence and clear-sky reference are known analytically; mixing them into a learning problem lets the learner memorise the clock instead of the atmosphere.
  • Reanalysis is not measurement. Grid-cell averages differ systematically from point observations; this must be surfaced, not hidden.
  • Consumption archetypes are approximations. Real interval-meter data would beat any archetype, and the platform says so when it uses one.

3Problem Statement

Anyone considering solar — a farmer, a homeowner, a shopkeeper, a facility manager — needs to answer four practical questions before spending money:

  1. How much energy can I generate here, per day and per year?
  2. How much of my consumption does that offset, and when does the mismatch fall?
  3. What will it cost, and how long will it take to pay back?
  4. How confident am I in each of these answers, given what I do and do not know?

The available tools fail these questions in three characteristic ways. First, they return one national or regional number rather than one specific to the user's coordinates — so a farm in a monsoon belt and a farm in a desert receive the same result. Second, they report a single point estimate as if it were measured, giving no signal that the actual value in any particular year may be 15 % above or below it. Third, they show none of the assumptions behind the number, so the user has no way to sanity-check it or to update it as their situation changes.

What the platform must therefore do

  • Answer per-location. Every calculation must run against the actual weather record at the supplied coordinates, not a regional lookup.
  • Answer per-user. The interview must adapt to what the user is trying to do — a farm question is not a home question — and must let every technical question be declined without producing a garbage answer.
  • Attach a range. Every headline number must carry an honest uncertainty band built from named components, not a round ± 10 %.
  • Show its working. Every assumption used must be recorded and displayed, and changing any of them must move every dependent number.
  • Refuse to fabricate. Where the platform cannot know something (e.g. because no metered generation was supplied to validate against), it must say so in the interface rather than silently substituting a default.
Reference-app failure that shaped this brief: The predecessor application returned 16.79 kWh alongside 0 % stated irradiance and gave the same figure for 06:51 and 13:51. Both are recorded in docs/REFERENCE_AUDIT.md. The platform's design decisions — time-aware validation, physical constraints applied after inference, explicit assumption ledger — exist so that neither failure can recur in Helios.

4Objectives

Primary objectives

  1. Deliver location-specific solar generation estimates using the observed hourly weather record at the user's supplied coordinates, not a regional average.
  2. Adapt the questionnaire to six user categories (home, farm, shop, commercial/industrial, institution, exploring) with different questions, defaults and result emphasis.
  3. Attach measured uncertainty to every headline number, decomposed into weather variability, resource error, model error and per-assumption components.
  4. Compute an energy balance and finances: hourly self-consumption and export, battery dispatch/sizing where requested, tariff-aware savings, payback, ROI, LCOE and lifetime CO2 avoided.
  5. Support three goals: sizing a planned system, describing an existing one, and comparing scenarios side-by-side.
  6. Produce a shareable, saved estimate with a stable URL, a plain-text report and an editable assumption ledger.
  7. Provide a research console that trains and evaluates ten scikit-learn model families with time-aware validation, prediction intervals and reproducibility manifests.

Secondary objectives

  1. Run keyless. Every upstream service used (Open-Meteo Archive and Geocoding, OpenStreetMap Nominatim) is public; no API keys and no accounts are required.
  2. Localise gracefully. Interview strings are held as data (not in components) so a future translator can add Telugu or Tamil without editing React.
  3. Fit into a rural context. Mobile-first layout, touch-friendly controls, tolerance of dropped GPS permission, an offline-tolerant map with a Leaflet swap.
  4. Never present modelled figures as measurements. No metered PV output was available, so the interface labels PV figures as physically modelled and uses no synthetic "validation" against fabricated data.
  5. Keep the surfaces separate. The consumer flow and the console flow do not share a palette, a route, a wording register, or a reader.
  6. Preserve provenance. Every weather fetch is cached to disk and every model run is written to an experiment store with a dataset fingerprint (SHA-256 of the feature matrix + target + names + period).

Representative workflows

Farmer with a 5 HP pump and 3 acres

Answer Farm, drop a pin on the well, tell the interview it is a 5 HP pump on a 20 m head. Everything else can be skipped. The estimate returns the daily generation, the number of pump-hours that generation supports, and how many m3 of water that moves in the driest month versus the monsoon. A subsidy-aware caveat appears if the location's default agricultural tariff is subsidised.

Homeowner with a 3 000 INR monthly bill and 40 m2 of usable roof

Answer Home, enter the bill, enter the roof area. The engine picks the best tilt/azimuth for the location, recommends a panel count that hits the bill (subject to space), returns monthly savings and payback, and asks whether to add battery storage.

Facility manager comparing 100 kWp, 150 kWp, and 200 kWp options

Fill in the details once (facility type, roof, tariff), then use POST /api/estimate/compare to score all three capacities against the same weather, producing a table of annual kWh, offset %, CAPEX, payback and ROI.

Owner of an existing 5 kWp array

Set goal to Existing, enter the panel count and their rated wattage. The sizer is bypassed — capacity is a measurement of what is on the roof, not a recommendation — and the engine produces the true expected production of the installed system, giving the owner a benchmark against their actual bills.

6System Overview

Helios is a two-tier web application. A Python 3.11 backend built on FastAPI exposes a typed JSON API; a Next.js 15 frontend consumes it. All state is persisted server-side as JSON on local disk — there is no database and no user account system. Two external services are called: the Open-Meteo Historical Weather API for hourly reanalysis, and OpenStreetMap Nominatim for reverse-geocoding a dropped map pin. Both are keyless.

7System Architecture

Presentation Layer

Next.js 15 App Router with React 19 and TypeScript. Two route groups keep the surfaces separate: app/(site)/ hosts the consumer flow (landing, start, estimate, result, compare, resources, projects, how-it-works, about) with a light palette, while app/advanced/ hosts the analysis console with a dark instrument palette and no shared chrome. Styling is Tailwind CSS 3.4 with a hand-tuned token scheme; there is no charting library — every plot in both surfaces is a hand-rolled SVG in components/charts/ and components/result/charts.tsx.

Application / API Layer

FastAPI application backend/app/main.py assembles four routers:

  • app.api.routes.meta  — health, catalogue, interview metadata, data-source manifest, place search.
  • app.api.routes.estimate  — consumer surface: create/read/update/delete/rename an estimate, run a comparison, produce a professional report.
  • app.api.routes.analysis  — console surface: create an analysis, then query its quality, predictions, performance, intervals, explanation, anomalies, forecast, scenarios and report subresources.
  • app.api.routes.experiments  — list, compare and delete persisted experiments.

Cross-cutting concerns live in main.py: a fixed-window in-process rate limiter, a middleware that stamps every response with a request ID and elapsed time, security headers (X-Content-Type-Options, Referrer-Policy, X-Frame-Options), and error translators that turn Pydantic validation failures, upstream data-source errors and internal exceptions into a structured envelope with error, message, detail, remedy and (for validation) field_errors.

Data Layer

No relational database. Two on-disk stores keep server state:

  • Weather & geocoding cache — JSON files keyed by a SHA-256 of the request URL + parameters, with a configurable TTL. Every upstream call goes through this cache, so an orientation search that evaluates twenty candidate tilts still fetches the weather only once.
  • Estimate store — JSON records under backend/var/estimates/, addressable by opaque estimate ID. Records include the full payload, the original request snapshot (for update), the label and timestamps. A retention sweep at startup prunes records past the configurable window.
  • Experiment store — JSON records for every training run, carrying the dataset fingerprint, metrics, folds, baselines and manifest; used by the console's Experiments view.

Prediction Layer

Two paths share a single physical chain and a single feature pipeline:

  • Fast path (consumer) — app/estimate/climatology.py runs the physical chain over 3 years of ERA5 hourly weather at the coordinates. No model is trained; inter-annual variability is measured, not assumed.
  • Forward-looking path (console) — app/models/trainer.py trains a scikit-learn estimator on a feature set built from the same weather (see § 19), splits chronologically with a 24-hour embargo, cross-validates with rolling origins, and calibrates a prediction interval using Conformalised Quantile Regression.

Deliberate omissions

  • No charting library. Every visualisation is a hand-written SVG so the design and print output are under full control and the bundle stays small.
  • No state-management library. React state plus localStorage covers every wizard step.
  • No deep-learning runtime. The model set intentionally stops at scikit-learn ensembles; sequence models (LSTM / BiGRU) are declared as future work in app/models/registry.py::future_work().
  • No third-party auth. There are no user accounts; estimates are addressable by an opaque, unlisted URL.

10User Experience and Workflow

The consumer flow is a linear wizard with a single decision point at the top: what kind of user, and what goal. Every subsequent step adapts to those answers.

Figure 10.1  —  End-to-end user workflow. The same result stage is reached by all six personas; the intermediate steps differ in question wording, defaults, and which cards are shown in the result.

Wizard behaviour

  • Skippable everywhere. Every technical question includes an "I don't know" or "help me estimate" branch. Skipping is honest, not free: the assumption that fills the gap is recorded in the ledger, and the uncertainty band widens.
  • Draft persistence. Answers are saved to localStorage as the user types (lib/draft.ts), so a page refresh, a phone lock or a network blip does not restart the interview.
  • Progressive disclosure. Quick mode presents the essentials only; Detailed mode reveals orientation, inverter, loss overrides and degradation.
  • Deterministic loading stages. The LoadingStages component reflects real work: location resolution → weather → orientation search → final yield → balance → economics. The stages are never marked finished before the backend reports them done (enforced by frontend/tests/components.test.tsx).

11Adaptive Questionnaire

The interview is data, not code. backend/app/estimate/personas.py (1 256 lines) declares every question, its wording, its help text, a spoken form for a future voice interface, and — where the answer is technical — an explicit "I don't know" branch that names the assumption the platform will use instead. The React components render whatever GET /api/meta/interview returns.

Question kinds

Twelve question kinds cover the interview:

  • single_choice radio-group selection
  • multi_choice checkbox group
  • number numeric input
  • currency money input with regional symbol

13Location System

The location step accepts three inputs interchangeably, and reconciles them all to a resolved Location object with latitude, longitude, elevation, timezone, country, ISO 2 country code and admin 1 region.

Input methods

  1. Place search. Typed query → GET /api/meta/place_search?q=… → Open-Meteo Geocoding (GeoNames source). Returns up to 10 candidates ordered by population, each with country, admin1, timezone and elevation.
  2. GPS auto-locate. Browser Geolocation API → reverse geocode via GET /api/locations/reverse (OpenStreetMap Nominatim). Coordinates are rounded before the reverse-geocode request — this improves cache hit rate and sends less location precision to a third party.
  3. Map-pin drop / polygon draw. The hand-rolled Web Mercator tile map in components/estimate/map/TileMap.tsx supports a single pin (for the site) and an optional polygon (for available area). Polygon area is computed on the client using the shoelace formula on projected coordinates — correctness of that projection is enforced by frontend/tests/logic.test.ts.

What happens after a location is selected

  1. Backend resolve_location() normalises coordinates to a Location, adding country code, timezone and elevation from the geocoder.
  2. The country code chooses currency (tariffs.currency_for_country) and default tariff (tariffs.default_tariff). Both are recorded in the ledger as provenance="regional_default" and are editable.
  3. The engine fetches 3 years of hourly ERA5 weather at those coordinates (climatology.fetch_history) — a single fetch that is reused for the orientation search, the reference yield and the final yield.
  4. All timestamps are converted from UTC to local clock time using the timezone the geocoder supplied; if none was supplied, a longitude-based solar-time offset is used, which is the right fallback for a solar calculation because it puts noon at solar noon.

Fallback behaviour

  • Denied GPS permission → the location step falls back cleanly to search + map; tested end-to-end.
  • Unknown place-search query → the API returns a structured 404 with a remedy message ("Try a larger nearby city, add a country, or switch to coordinate entry").
  • Reverse geocode failure → the coordinate is used verbatim with a synthesised label like "27.18°N, 78.04°E"; the estimate still runs.
  • Missing timezone → longitude-derived offset applied silently.

Map engine swap

The default map (TileMap.tsx, ~250 LOC, zero external runtime dependencies) supports pin, polygon and pan/zoom. Setting the environment variable NEXT_PUBLIC_MAP_ENGINE=leaflet at build time swaps in a Leaflet-backed adapter behind the same MapPicker interface. Leaflet is dynamically imported so it is absent from every bundle unless selected.

Privacy note: Coordinates are rounded before being sent to OpenStreetMap Nominatim. The consumer surface stores no location data server-side except inside the opaque saved-estimate record the user chose to save.

16Panel Quantity and System Capacity

The identity is intentionally exact:

DC capacity (kWp) = Number of panels × Rated power per panel (W) ÷ 1000

— and it is the panel count, not the sizer's target capacity, that wins. A recommendation of 15.4 kWp becomes an array of 28 panels of 550 W = 15.40 kWp exactly; a recommendation of 15.5 kWp with the same panel becomes 29 panels = 15.95 kWp. Every downstream figure is computed for the array that will actually exist.

Effects of panel count on downstream figures

  • DC capacity — linear.
  • Annual generation — approximately linear in capacity, less inverter clipping. Clipping grows non-linearly as DC/AC ratio rises above 1.2.
  • Roof area required — count × panel area ÷ usable fraction (usable fraction depends on mount type; e.g. tilted-open-rack rooftop is lower than commercial flat roof).
  • Inverter sizing — AC capacity defaults to DC / 1.2; explicit values from the user override.
  • Clipping — every hour with DC · ηinv above AC cap is clipped; the fraction is reported and warns above 2 %.
  • Financial outputs — CAPEX per kWp is a per-region default that decreases mildly with size (bulk discount); annual savings scale with generation subject to self-consumption and export rules.

Why the consumer path does not train a model

A consumer asks what a system will produce in a typical year. That is a climatology question, and the honest answer comes from running the published physical chain over years of observed weather. Training a model to forecast hour-ahead irradiance and then averaging its predictions adds nothing to an aggregate the physical chain already produces — and would cost about thirty seconds of training to say the same thing.

The deterministic physical chain (used by both paths)

  1. Solar geometry — NOAA Solar Calculator formulation (Michalsky 1988; NOAA ESRL). Accuracy ~0.01° over 1900–2100. Outputs zenith, azimuth, declination, equation of time, hour angle. Solar position is evaluated at the interval midpoint (−30 min from the label) because the archive's hourly irradiance is a preceding-hour average — a convention determined empirically in scripts/calibrate_interval.py (see § 18).
  2. Extraterrestrial irradiance — solar constant 1 361 W/m2 modulated by orbital eccentricity (±3.3 % over the year).
  3. Clear-sky reference — Haurwitz (1945) model, single parameter, no site tuning. Used to form the clear-sky index kt = GHI / GHIcs.
  4. DHI/DNI decomposition — Erbs et al. (1982) piecewise diffuse-fraction, keyed on kt and clipped to [0, 1].
  5. Transposition to plane-of-array — HDKR (Hay-Davies-Klucher-Reindl) anisotropic sky model. Adds circumsolar brightening and horizon brightening on top of an isotropic diffuse assumption.
  6. Cell temperature — Faiman (2008): Tcell = Tair + POA / (u0 + u1·vwind) with u0 = 25 W/(m2K), u1 = 6.84 W/(m3s K).
  7. DC power — PVWatts v5 (Dobos 2014): Pdc = (POA/1000) · Prated · [1 + γ(Tcell−25)] · (1−L) where L is the total system-losses fraction (dust, shading, wiring, mismatch, availability, LID; combined multiplicatively).
  8. Inverter and clipping — Pac,uncapped = Pdc · ηinv; Pac = min(Pac,uncapped, PAC-cap). The fraction of daylight hours in which clipping occurred is reported.

How the consumer path aggregates

  1. Fetch 3 years of hourly ERA5 at the coordinates (default; configurable).
  2. Drop hours missing any required variable (GHI, Tair, wind); imputation is never used.
  3. Search tilt / azimuth against the same weather using the same physical chain at 1 kWp (see sizing.optimal_orientation).
  4. Run the chain twice: once at 1 kWp to obtain specific yield (needed for capacity recommendation), then once at the sized capacity (needed to capture inverter clipping, which is not capacity-invariant).
  5. Aggregate hourly AC power into (a) annual energy, (b) monthly means and inter-annual standard deviations, (c) mean diurnal profile, (d) per-month diurnal profiles.
  6. Compute performance ratio, capacity factor, specific yield, mean POA/GHI, and clipped fraction.

Uncertainty attached to the point figure

See § 18 and § 23 for the full decomposition. Briefly: the range combines measured inter-annual variability, an order-of-magnitude resource term (grid vs point), a model term for the conversion chain itself, and per-assumption components that grow whenever the user skipped a question. Combination is in quadrature (independent components).

What the fast path deliberately does not do

  • Does not use lagged values of the target. A day-ahead forecast has no access to the recent observed irradiance; using it would inflate offline metrics without helping in deployment.
  • Does not statistically truncate the target (no IQR clipping). Physical-range validation only.
  • Does not impute missing values. Incomplete hours are dropped and reported.

18Mathematical Model — Formulas Used

18.1 System capacity

P_rated_kWp = N_panels × W_panel / 1000

18.2 Solar geometry

Julian day from Unix epoch (avoiding calendar-branch bugs):

JD = seconds_since_epoch / 86400 + 2 440 587.5
JC = (JD − 2 451 545) / 36 525          # Julian century since J2000

Solar declination and equation of time follow the NOAA Solar Calculator formulation. Zenith and azimuth are obtained from:

cos(z)  = sin(φ)·sin(δ) + cos(φ)·cos(δ)·cos(H)
z_app   = z − Δrefract(z)               # atmospheric refraction correction

where φ is latitude, δ declination, and H hour-angle in radians.

18.3 Extraterrestrial normal irradiance

E_0n = 1361 · [1 + 0.033 · cos(2π · DOY / 365)]    W/m²

18.4 Clear-sky GHI (Haurwitz 1945)

GHI_cs = 1098 · cos(z_app) · exp(−0.059 / cos(z_app))     W/m²

18.5 Clear-sky index

k_t = clip(GHI / GHI_cs, 0, 1.5)     # cap accommodates cloud enhancement

18.6 Erbs decomposition

With kT = GHI / E0h (E0h the horizontal extraterrestrial):

d_f = { 1 − 0.09·k_T                                          if k_T ≤ 0.22
      { 0.9511 − 0.1604·k_T + 4.388·k_T² − 16.638·k_T³ + 12.336·k_T⁴   if 0.22 < k_T ≤ 0.80
      { 0.165                                                if k_T > 0.80

DHI = GHI · d_f
DNI = (GHI − DHI) / cos(z_app)

18.7 Plane-of-array via HDKR

A_i  = DNI / E_0n                       # anisotropy index
R_b  = cos(AOI) / cos(z_app)
f    = √(DNI·cos(z_app) / GHI)          # horizon-brightening modulator

POA = DNI · cos(AOI)                                          # beam
    + DHI · [ (1−A_i)·(1+cos β)/2 · (1 + f·sin³(β/2))         # sky diffuse
              + A_i · R_b ]
    + GHI · ρ · (1 − cos β)/2                                 # ground-reflected

where β is surface tilt, ρ = 0.20 is default albedo, and AOI is angle of incidence:

cos(AOI) = cos(z)·cos(β) + sin(z)·sin(β)·cos(γ_s − γ)

with γ the surface azimuth and γs the solar azimuth.

18.8 Cell temperature (Faiman 2008)

T_cell = T_air + POA / (u_0 + u_1 · v_wind)
u_0 = 25   W/(m²·K)   ; u_1 = 6.84   W/(m³·s·K)

18.9 DC power (PVWatts v5)

P_dc = (POA / 1000) · P_rated_kWp · [1 + γ · (T_cell − 25)] · (1 − L)

with γ the temperature coefficient (per °C) and L the combined system-losses fraction.

18.10 Losses (combined multiplicatively)

1 − L = ∏_i (1 − L_i)      i ∈ {dust, shading, wiring, mismatch, availability, LID, …}

18.11 Inverter and clipping

P_ac_uncapped = P_dc · η_inv
P_ac          = min(P_ac_uncapped, P_AC_cap)
clipped_h     = 1[P_ac_uncapped > P_AC_cap]

19Machine Learning Model (Analysis Console)

Scope note: Machine learning applies only to the research console (/advanced), which trains a model to forecast hourly irradiance for validation and interval calibration. The consumer estimate does not use a trained model — it runs the physical chain over years of observed weather (see § 17).

Target

Clear-sky index kt = GHI / GHIcs, per Hobbs & Joshi. Dividing out the deterministic diurnal and seasonal signal means the model only has to learn atmospheric attenuation — the genuinely uncertain part. Predictions are converted back to W/m2 after inference for reporting.

Input features

  • Meteorological (from ERA5): temperature, relative humidity, dew point, surface pressure, wind speed, wind direction, cloud cover, precipitation.
  • Solar geometry (computed in closed form): zenith, azimuth, angle of incidence, optical air mass, clear-sky GHI, extraterrestrial normal irradiance.
  • Cyclical time encodings: sin/cos of hour-of-day and day-of-year.
  • Weather regime label: sunny / cloudy / other, derived from cloud cover and clear-sky index.

No lagged values of the target are used. At a day-ahead issue time the recent observed irradiance does not exist, so an autoregressive feature would improve every offline metric while being unavailable in deployment.

Preprocessing

  • Night hours (zenith ≥ 87°) removed; predicting zero after dark is trivial and inflates R2.
  • Missing values dropped, never imputed.
  • Outliers: physical-range validation only; no IQR truncation of the target.
  • Scaling: inside the model pipeline (StandardScaler), refitted per fold so test statistics never leak into training.

Validation

  • Chronological hold-out with a 24-hour embargo gap (splitters.chronological_split).
  • Rolling-origin cross-validation with the same embargo (splitters.rolling_origin_splits).
  • Five-check leakage audit: target, future information, preprocessing, boundary contamination, trivial observations.
  • Physical-bound post-processing: predictions above 1.25 × GHIcs or below zero are clipped; the clipped-fraction is reported.

Prediction intervals

Nominal 80 % central intervals via Conformalised Quantile Regression (uncertainty.conformalized_quantile_regression). On two years at Hyderabad, plain quantile regression measured 66.3 % empirical coverage against the 80 % nominal; after conformal calibration, 80.2 %, within 2 points across all three weather regimes. Coverage is reported per regime as well as overall, because a model can hit 80 % overall while badly under-covering the cloudy hours that matter most operationally.

Metrics reported

MAE, RMSE, MBE, R2, rRMSE, rMAE, MAPE, sMAPE, forecast skill score; probabilistic: pinball loss, PICP, PINAW, CRPS. Two honesty notes carried into the UI: NSE and R2 are the same quantity (labelled aliased); MAPE is unstable for irradiance (denominator → 0 at sunrise) and always accompanied by its exclusion count.

Reproducibility manifest

Every run persists a manifest with the dataset fingerprint (SHA-256 of the feature matrix + target + names + period), the random seed, library versions (numpy, pandas, scikit-learn), the platform string, and the exact preprocessing decisions. The comparison endpoint refuses to rank runs that are not comparable (different locations, periods or targets).

Reanalysis vs measurement: ERA5 is a grid-cell average and differs systematically from a pyranometer on the user's roof. Results here are therefore not directly comparable to studies using measured irradiance. The platform labels every figure as physically modelled from reanalysis and, because no metered PV output was available, does not claim validation against measured generation.

23Uncertainty and Limitations

Uncertainty band construction

For the consumer estimate, uncertainty is assembled from four named component categories in estimate/uncertainty.py:

  1. Weather variability — the standard deviation of the years in the record, converted to a relative figure. This is measured; it is usually the largest term and it is irreducible.
  2. Resource-data uncertainty — a ~5 % order-of-magnitude term standing in for the gap between a reanalysis grid cell and a rooftop pyranometer.
  3. Conversion-model uncertainty — a ~5 % term covering the physical chain (Erbs, HDKR, Faiman, PVWatts) applied to correct inputs.
  4. Assumption components — per-question terms that grow whenever the user could not answer. Skipping shading level adds a term; skipping orientation adds a term; using a bill route with the regional-default tariff adds a term.

Components combine in quadrature. The resulting relative σ is applied to give an 80 % central band under a normal approximation (z = 1.2816). The 80 % nominal is used deliberately: 95 % on a solar estimate is so wide it stops being decision-useful, and the console's conformal intervals use the same 80 % so two numbers on two screens mean the same thing.

Confidence rating

Alongside the band the platform assigns a three-level confidence: high, medium, low. It is derived from data completeness, the number of complete calendar years in the record, whether shading and orientation were declared, and whether the user provided demand. A low rating carries a plain-language explanation and a list of the reducible components with instructions for how to reduce them ("Add your electricity bill", "Tell us your roof orientation").

Console-side intervals

Conformalised Quantile Regression, calibrated on a hold-out slice of training data. Empirical coverage is reported overall and per weather regime; substantial deviation from nominal is surfaced as a warning.

Known limitations

  1. Reanalysis, not measurement. ERA5 grid-cell means differ from point observations by amounts that vary with terrain and climate.
  2. No metered PV output was available. All PV figures are physically modelled from irradiance and not validated against measured generation. The interface says so.
  3. Weather-forecast error not included in intervals. The intervals cover model error given the supplied weather; they exclude error in the weather forecast itself, which grows with horizon.
  4. Trained per location. No cross-location generalisation of models is claimed.
  5. Marginal, not conditional, coverage. Conformal PICP is a marginal guarantee; it assumes exchangeability that a seasonal series satisfies only approximately.
  6. Missing variables from source. Aerosol optical depth, sunshine duration and wind-direction standard deviation are named in the source research but unavailable from the current data source; the interface surfaces this rather than silently omitting them.
  7. Bifacial modelling is simplified. A rear-side yield adder is used; a full view-factor bifacial model is future work.
  8. Hourly load archetypes. Six user-type shapes cover the interview, but real interval-meter data would beat them and the interface says so.
  9. Uncertainty components are treated as independent (quadrature). They are not perfectly independent, so the combined figure is a slight understatement, stated openly.
  10. Financial modelling omits financing/interest, subsidies and rebates (they vary by scheme and expire), demand charges on commercial connections, and taxes; each is stated in the caveats rather than silently assumed away.

24Validation and Error Handling

Frontend validation

  • Field-level types & ranges (positive numbers, area unit sanity, coordinate bounds).
  • Rejection messages state what to type instead, not "invalid"; e.g. "Enter a positive number of panels" rather than "value error".
  • Never blocks progression on optional fields; every technical question offers an escape route.
  • Location step handles denied GPS permission with a switch to search/map without an error dialog.

Backend validation

  • Pydantic schemas in backend/app/schemas/estimate.py and schemas/models.py validate every request. Custom validators enforce domain rules (positive capacity, tilt in [0, 90], azimuth in [0, 360)).
  • Pipeline pre-conditions in the engine raise ValueError with user-facing messages, caught at the route boundary and returned as 422s.
  • Physical validation of PVSystem in features/solar_geometry.py::PVSystem.__post_init__.
  • Data-quality engine (quality/engine.py) detects eight distinct corruption modes (missing runs, all-zero days, impossible temperatures, stalled sensors, wrong-hemisphere daylight, etc.) and scores the record.
  • Leakage audit in the console runs a five-check test (target, future information, preprocessing, boundary contamination, trivial observations) and reports the mechanism preventing each.

Error envelope

Every error the client sees uses the same shape:

{
  "error": "validation_error",
  "message": "location: Tell us where the system will be — search…",
  "remedy": "Correct the highlighted fields and resubmit.",
  "field_errors": [ { "field": "location", "message": "…", "type": "missing" } ]

The frontend renders message, remedy and any field_errors verbatim — the backend is where the domain knowledge lives, and its wording is preserved rather than substituted with something generic.

25Security

The platform runs against keyless upstream services and holds no user accounts, so its attack surface is narrower than a typical SaaS. Actual measures in place:

  • No secrets required or stored. No API keys, no OAuth. Environment variables carry only configuration (endpoints, cache directory, CORS origin).
  • Environment-driven configuration. backend/app/config.py reads all tunables from the environment with safe defaults; secrets, if any were ever added, would live only in the environment.
  • CORS scoped. SOLAR_CORS_ORIGINS defines the accepted origins; production deployments should set this to the deployed frontend origin only.
  • Rate limiting. Fixed-window per-client in-process limiter in main.py. The limits are configurable (SOLAR_RATE_LIMIT_REQUESTS, SOLAR_RATE_LIMIT_WINDOW_S). The README states clearly that this is not a substitute for a gateway limiter.
  • Security headers on every response: X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY.
  • Request ID stamping. Every response carries an X-Request-ID header (also stamped in server logs) for traceability without exposing internals.
  • Structured error output. Stack traces are never returned to the client; internal errors carry only the request ID.
  • Input validation. Every request goes through Pydantic; custom validators enforce domain rules; upstream URLs and parameters are constructed server-side.
  • Coordinate rounding before reverse-geocoding. Third parties receive lower-precision coordinates than the ones the user supplies.
  • Estimate URLs are opaque. Saved-estimate IDs are unguessable tokens; there is no listing endpoint that enumerates other users' estimates.
  • Retention sweep at startup. Old estimates are pruned past a configurable window (SOLAR_STORE_ESTIMATE_RETENTION_DAYS).

Not implemented (deliberately)

  • No authentication or authorisation — there are no users.
  • No third-party analytics or telemetry.
  • No client-side secrets. The frontend never talks to Open-Meteo or Nominatim directly.

26Performance and Responsiveness

Backend performance

  • Weather cache — every Open-Meteo response is cached to disk by URL+params SHA-256. Repeat requests avoid the network entirely.
  • Single fetch per estimate — the orientation search, the reference-yield calculation and the final-yield calculation all reuse the same in-memory DataFrame.
  • Vectorised physics — the whole chain runs in NumPy; solar-position is computed once for the whole index; no Python loops over hours.
  • Latency in practice — ~1 s for a cached location, ~15 s for a new location (dominated by the Open-Meteo fetch), 10–40 s for a full console analysis (train + CV + calibrate + evaluate).
  • Response timing header — X-Response-Time-ms on every response; slow requests (> 5 s) are also logged.

Frontend performance

  • No charting library — SVG charts add ~0 kB of runtime dependencies.
  • Dynamic Leaflet import — the Leaflet swap is dynamically loaded, so it is absent from every bundle unless NEXT_PUBLIC_MAP_ENGINE=leaflet.
  • Server components for the shell — the landing page and static sections are server-rendered; only interactive components ship JavaScript.
  • Draft persistence in localStorage — no server round-trip for wizard progress.
  • Deterministic loading stages — user sees real progress against real work; no spinner masquerading as motion.

Responsive rendering

Tailwind's breakpoints are used throughout with a mobile-first layout in the consumer surface. Charts scale with their container. Touch targets on maps and wizard inputs are sized to the minimum recommended for touch (44 CSS px). The console surface is laptop-and-up (it presents dense tables that do not compress well onto a phone).

32Conclusion

Helios pairs a rigorous physical solar model with a genuinely usable consumer surface, without diluting either. It answers the practical question a homeowner, farmer, business or facility manager actually has — how much energy will this generate, what does it save, and how confident can I be — using the actual weather record at the supplied coordinates rather than a national average, and returns the answer with an honest uncertainty band built from measured components. It also carries a full research console: ten scikit-learn model families, time-aware validation with a leakage audit, conformal prediction intervals, and reproducible experiment records.

The technical significance of the project is not any single algorithm — the physical chain is textbook (Erbs, HDKR, Faiman, PVWatts) and the estimators are scikit-learn. It is that every number the interface shows can be traced back to an input, every default is on the table for the user to override, and nothing modelled is ever presented as measured. Those three constraints produced the specific architectural choices documented above — the assumption ledger, the ban on target-lag features, the panel-count-wins rule, the empirically determined interval offset, the conformal calibration of prediction intervals, the comparison endpoint that refuses to rank incomparable runs.

Practically, the platform runs on a laptop with no API keys, produces an answer in a few seconds, and ships with 270+ automated tests, an ASGI-ready backend and a Next.js frontend that can be deployed behind any reverse proxy. Its future potential lies in adding real-time monitoring, ground-truth validation, additional languages, and the sequence-model class explicitly declared as future work in the model registry.
